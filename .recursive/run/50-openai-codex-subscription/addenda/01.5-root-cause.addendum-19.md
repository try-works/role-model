## Root Cause

The current runtime collapses two different capability contracts into one:

1. OpenAI Responses hosted `web_search`
2. generic provider tool calling that can support a runtime-executed `web_search` tool

In code today:

- `mapResponsesRequest()` converts every non-function Responses tool into
  `RuntimeExecutionHostedToolDefinition`
- `filterAllowEndpointsForResponsesHostedTools()` then narrows the candidate pool to
  endpoints in the OpenAI Codex Subscription support matrix
- `provider-openai` forces any request containing hosted tools onto the `/responses`
  path

That behavior is correct for exact OpenAI Responses hosted-tool requests, but wrong for
mixed or non-OpenAI pools when the actual user intent is simply "a web-search-capable
turn."

Kimi and DeepSeek vendor docs both support normal tool calls where the runtime executes
the tools and returns the results to the model. So excluding those endpoints from
web-search turns is not caused by missing model capability. It is caused by request
contract misclassification.

## Required Correction

The runtime must classify `web_search` requests by execution contract:

1. preserve the OpenAI-hosted contract when the selected endpoint pool truly supports it
2. otherwise translate the request into a runtime-executed function tool contract so
   OpenAI-compatible function-calling providers such as Kimi and DeepSeek remain
   eligible

That correction also requires a real runtime `web_search` tool implementation. Without
that execution path, broadening routing eligibility would only route requests into
providers that cannot complete the turn.
