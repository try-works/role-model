Scope note: make hosted web-search capability metadata transport-aware for OpenAI, Kimi, and DeepSeek without inventing a DeepSeek native contract on the current OpenAI-compatible runtime surface.

## Root Cause

The runtime currently mixes together two different concepts:

1. generic tool-calling capability
2. provider-native hosted web-search contracts

Those are not interchangeable.

Current verified provider facts are:

1. OpenAI Codex Subscription GPT-5.3+ supports the normalized hosted Responses
   `web_search` contract that this runtime already models.
2. Kimi supports provider-native web search on its OpenAI-compatible
   chat-completions surface using `type: "builtin_function"` and
   `function.name: "$web_search"`, with thinking disabled.
3. DeepSeek documents native web search on its Anthropic / Claude Code surface,
   including `server_tool_use` / `web_search_tool_result` support, but that is not the
   same transport the runtime currently uses for DeepSeek endpoints.

So the current gap is not that Kimi or DeepSeek lack tool capability metadata. The gap
is that the runtime and docs do not state clearly enough which web-search contracts are:

1. native on the current runtime transport
2. documented by the provider but only on a different transport
3. satisfied today through runtime-managed function-tool fallback

That ambiguity makes the docs inaccurate and makes future routing changes risky.

## Required Correction

The runtime must represent hosted web-search support as transport-aware metadata:

1. OpenAI exact native contract:
   `openai.responses.web_search`
2. Kimi exact native contract:
   `moonshot.chat.builtin_web_search`
3. DeepSeek documented-but-not-current-runtime-native contract:
   `deepseek.anthropic.server_web_search`

Then the bridge must continue to route using three explicit outcomes:

1. use the native hosted contract when the exact endpoint pool supports it on the active
   runtime transport
2. keep endpoints eligible through runtime-managed `web_search` fallback when they expose
   ordinary tool calling on the active transport
3. avoid claiming provider-native support for a transport the runtime does not execute

This is primarily a metadata, verification, and documentation correction, not a request
to force DeepSeek onto an unsupported OpenAI-surface hosted-search contract.
