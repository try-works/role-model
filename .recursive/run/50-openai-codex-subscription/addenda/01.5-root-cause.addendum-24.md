## Root Cause

After addendum `23`, deterministic regression coverage and bridge logic improved, but live `3462`
verification still showed incomplete DeepSeek convergence:

1. `chatgpt/gpt-5.4` completed to a final answer.
2. `moonshot/kimi-k2.7-code` completed to a final answer.
3. `deepseek/deepseek-v4-flash` returned DSML `web_open` assistant markup as final output.
4. `deepseek/deepseek-v4-pro` alternated between:
   - partial prose plus DSML `web_open`
   - DSML `web_browse`
   - or a degraded fallback answer without the requested live price

DeepSeek can legitimately ask to open or browse a page after searching, but that does not mean the
router runtime should become a general browser host. For consumer apps like Craft Agents and Pi that
already provide DeepSeek tool execution, the correct runtime responsibility is narrower:

- detect provider-specific DSML tool markup
- normalize it into consumer-visible tool-call records
- preserve enough structured arguments for the consumer to execute and continue the turn

So the remaining failure is primarily a bridge normalization gap:

- DeepSeek emits `web_open` / `web_browse` in DSML markup
- the bridge currently leaves that markup in assistant text
- the public HTTP surface therefore leaks provider-specific syntax instead of structured tool calls
