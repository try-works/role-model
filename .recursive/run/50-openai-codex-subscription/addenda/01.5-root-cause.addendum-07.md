Scope note: This addendum covers the remaining controller-routing contract failure after the timeout fix, plus the role/task UI hierarchy problem exposed during operator review.

## Live Failure Shape

After the default timeout remediation, intelligent alias routing no longer fails with `controller-timeout`. The live runtime now shows:

1. `routingDiagnostics.controllerRouting.active = true`
2. `routingDiagnostics.controllerRouting.fallbackApplied = true`
3. `routingDiagnostics.controllerRouting.fallbackReason = "invalid-controller-output"`

That means the controller request is executing, but the bridge still cannot reliably turn the returned guidance into runtime-safe routing directives.

## Concrete Root Cause

There are three coupled defects:

1. the controller prompt in `/role-model-router/apps/runtime-host-bridge/src/index.ts` does not constrain the model to the runtime's actual role ids, task types, capability ids, or supported strategy vocabulary
2. the bridge accepts only a weak free-form JSON contract, so the controller can emit semantically nearby but runtime-invalid labels such as `code_generation`, `capability_based`, or ad-hoc capability strings that do not exist in the live role policy
3. the operator UI in `/role-model-router/apps/runtime-ui/app/routes/control-roles.tsx` presents task types at the same first-layer level as roles, which makes the runtime task hierarchy harder to understand and harder to validate against controller guidance

The result is a gap between what the controller is told it may choose and what the runtime can actually honor.

## Why The Current Behavior Misroutes

The runtime already has enough information to guide the controller safely:

- live role ids
- live task definitions
- live capability vocabulary implied by those definitions
- existing strategy vocabulary supported by the bridge

But the current prompt does not give the controller that bounded list, and the current UI does not reinforce the same hierarchy for operators. So the controller invents labels that look right in plain English but are not runtime-valid. For example, a coding request can lead the controller toward a non-existent task label like `code-generation` instead of choosing an existing coding role such as `coder.patch`.

## UI Root Cause

The runtime role policy is hierarchical:

- roles are the top-level operator concept
- tasks belong underneath those roles

The current role catalog breaks that hierarchy by rendering supported task types directly on each role card and by keeping a separate task-first allowlist section. Operators see tasks immediately instead of first choosing a role and then drilling into task detail.

## Root Cause Summary

**Root Cause:** controller routing is underconstrained and UI hierarchy is flattened. The controller is not restricted to runtime-known roles, tasks, capabilities, and strategy values, and the Roles UI does not present the same role-first hierarchy that the runtime policy actually uses.

**Location:** `/role-model-router/apps/runtime-host-bridge/src/index.ts` and `/role-model-router/apps/runtime-ui/app/routes/control-roles.tsx`.

**Impact:** intelligent aliases fall back even after successful controller execution, coding requests are less likely to land on coder-eligible models, and operators cannot easily verify which tasks actually belong to a role.

## Fix Strategy

1. build a runtime-known controller choice set from role ids, task definitions, capabilities, endpoint ids, and supported strategy values
2. inject that allowlist and explicit guardrails into the controller prompt
3. normalize controller output so invalid fields are dropped instead of poisoning otherwise-valid guidance
4. keep controller selection role-first: if no exact task matches, allow the controller to pick only a valid role and omit task or capability fields
5. update the Roles UI so role cards show only role-level information initially and reveal task detail only after an explicit operator action
6. record a follow-up expansion plan for broader built-in role/task coverage without blocking the current contract fix

## Test Requirement

This fix requires:

- RED tests proving controller guidance is filtered to runtime-known roles, task types, capabilities, endpoint ids, and strategy values
- RED tests proving semantically partial but valid guidance still survives when invalid fields are dropped
- RED tests proving the Roles UI renders role-first and reveals task detail only after a `Task detail` action
- targeted runtime rebuild and routing verification after the bridge and UI changes land
