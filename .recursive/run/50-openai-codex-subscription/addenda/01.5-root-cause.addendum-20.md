## Root Cause

The current runtime still models hosted search as if there were only one normalized
contract:

1. OpenAI Responses `tools: [{ type: "web_search" }]`

That assumption is now too narrow.

Kimi documents a different provider-native hosted search contract on its OpenAI-compatible
chat-completions surface:

- tool declaration uses `type: "builtin_function"`
- hosted search tool name is `"$web_search"`
- the request must disable thinking
- the continuation contract expects the caller to submit the generated arguments back as
  the `role=tool` result so Kimi can complete the search server-side

DeepSeek also documents a provider-native web-search capability, but the verified doc is
currently tied to the Claude Code / Anthropic integration contract, not to the
OpenAI-compatible transport this runtime currently uses for DeepSeek endpoints.

So the runtime gap is twofold:

1. request shaping only preserves the OpenAI hosted contract
2. tool execution only knows local/runtime-owned tools, not Kimi's passthrough
   `"$web_search"` continuation shape

## Required Correction

The runtime must distinguish provider-native hosted-search contracts instead of collapsing
everything into `OpenAI hosted` versus `runtime tool fallback`.

Immediate implementation target:

1. keep exact OpenAI hosted search on Responses unchanged
2. add exact Kimi hosted search on chat-completions using `builtin_function.$web_search`
3. treat Kimi `"$web_search"` tool calls as passthrough executions so the continuation
   step has the correct tool result payload
4. keep DeepSeek on the current runtime-executed fallback path until the repo supports a
   verified DeepSeek-native hosted-search transport contract
