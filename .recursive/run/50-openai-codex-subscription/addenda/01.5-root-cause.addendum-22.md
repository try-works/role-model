## Root Cause

The current bridge has two distinct continuation gaps:

1. `executeBridgePlan()` runs provider execution once, executes any returned tool calls
   through the runtime tool registry, records those tool receipts, and then returns
   immediately without sending the tool results back into the same provider turn.
2. `mapChatCompletionsRequest()` still parses tools through `toToolDefinition()` with an
   OpenAI-function-only contract, so Kimi hosted `builtin_function` continuations can be
   rejected on the public `/v1/chat/completions` surface.

That means the bridge currently proves only the first half of the flow:

1. provider emits a tool call
2. runtime executes the tool
3. bridge stops

It does not complete the second half:

4. append assistant tool-call message plus tool result message
5. re-issue the turn to the already selected provider endpoint
6. continue until the provider returns a final assistant answer or a bounded loop limit is hit

This is why live testing showed:

1. OpenAI GPT-5.4 succeeds in one exact `responses` call because its native hosted search
   finishes in-provider.
2. DeepSeek V4 Flash / Pro enter a valid runtime-managed `web_search` path but return the
   first `tool_calls` turn to the caller.
3. Kimi K2.7 Code enters a valid provider-native `"$web_search"` path but also returns the
   first `tool_calls` turn, and manual chat-completions continuation can still hit the
   function-only parser restriction.

So the remaining blocker is not capability metadata or initial routing. The blocker is the
missing bounded multi-turn continuation loop on the bridge-owned HTTP surface.
