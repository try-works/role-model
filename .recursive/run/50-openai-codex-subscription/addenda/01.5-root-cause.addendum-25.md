## Root Cause

Live `3462` verification showed a split-brain result:

1. `/v1/models` still exposed `craft-ask.decision-only`, `craft-ask.hybrid`, and
   `craft-ask.remote-only`.
2. `%LOCALAPPDATA%/Role Model Runtime/state/runtime-config.yaml` still persisted those same legacy
   rows.
3. the current routing UI and operator intent no longer treat `craft-ask` as a valid strategy.

The leak came from two separate gaps:

1. `craft-ask.*` rows were not treated as legacy primary routing aliases in the canonical alias
   matrix path, so startup materialization preserved them like custom aliases.
2. parse-time canonicalization only rewrote primary aliases when exactly one alias row existed,
   leaving multi-alias persisted configs untouched.
3. even after in-memory normalization was repaired, startup only rewrote the YAML when alias
   materialization changed the config shape. A file that already had the full canonical
   decision/hybrid/remote matrix plus stale `craft-ask.*` rows therefore stayed dirty on disk.

So the bug was not the active routing matrix itself; it was the compatibility scrub path around
legacy persisted config.

## Evidence

- focused parse regression initially failed because `parseUnifiedRuntimeConfigText(...)` returned
  `craft-ask.remote-only` unchanged in a multi-alias payload
- focused startup regression initially failed because the persisted YAML still contained
  `craft-ask.decision-only`, `craft-ask.hybrid`, and `craft-ask.remote-only` when startup did not
  need any additional alias re-materialization
- live `3462` before the fix reproduced the same stale file behavior
