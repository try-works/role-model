Scope note: This addendum covers the remaining live `controller.remote-only` fallback after the strategy-compatibility patch landed and tests passed locally.

## Live Failure Shape After The Compat Patch

After rebuilding and relaunching the runtime on `http://127.0.0.1:3461`, fresh live requests still show:

1. `routingDiagnostics.routingMode.aliasMode = "controller"`
2. `routingDiagnostics.controllerRouting.active = true`
3. `routingDiagnostics.controllerRouting.fallbackApplied = true`
4. `routingDiagnostics.controllerRouting.fallbackReason = "invalid-controller-output"` on multiple requests

That means the earlier parser patch is necessary but not sufficient for the live runtime.

## Concrete Root Cause

**Root Cause:** the live controller sub-call currently uses a fixed `maxOutputTokens: 256` budget in `/role-model-router/apps/runtime-host-bridge/src/index.ts`. With the real controller prompt and live candidate inventory, that budget is too small for the assigned controller endpoint.

Direct reproduction against the assigned controller model (`deepseek/deepseek-v4-flash`) shows:

- with a lightweight probe and default sampling, the model can emit valid compact JSON
- with the controller-style request parameters actually used by the runtime (`temperature: 0`, `max_tokens: 256`, large bounded prompt), the endpoint returns:
  - `finish_reason: "length"`
  - `message.content: ""`

An empty content string parses to `null`, so the bridge classifies the result as `invalid-controller-output` even though the controller call itself succeeded at the transport layer.

## Why The Current Behavior Is Wrong

The runtime is treating a truncated controller response as if the model produced semantically invalid JSON. That hides the real operational cause:

1. the request is not malformed
2. the endpoint is not unavailable
3. the parser is not the only problem anymore
4. the controller budget is too tight for the live prompt envelope

As a result, operators see repeated `invalid-controller-output` fallbacks even when the remaining issue is response truncation.

## Evidence

Live runtime evidence after relaunch:

- five fresh `controller.remote-only` requests produced three `invalid-controller-output` fallbacks and two `controller-timeout` fallbacks
- a direct controller-model probe with controller-style parameters returned:
  - `status: 200`
  - `choices[0].message.content: ""`
  - `choices[0].finish_reason: "length"`

That explains the persisted live fallback reason exactly.

## Fix Strategy

1. add a RED regression that simulates a controller endpoint returning empty content when the runtime keeps the 256-token cap
2. raise the controller execution output budget to a safer bounded value for the current prompt size
3. keep the response compact and deterministic (`temperature: 0`) while allowing enough completion space for valid JSON
4. rebuild and relaunch the runtime, then re-check live `controller.remote-only` fallback reasons

## Test Requirement

This slice requires:

- a failing runtime-host-bridge regression that reproduces empty controller content under the old `256` budget
- a passing regression after the controller output budget is raised
- targeted bridge verification after rebuild
- live request-detail inspection on the relaunched runtime to confirm `invalid-controller-output` drops materially
