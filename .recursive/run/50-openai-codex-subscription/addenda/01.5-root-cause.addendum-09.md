## Live Failure Shape

Direct live probing against `http://127.0.0.1:3461` shows:

1. `POST /v1/chat/completions` with `model: "controller.remote-only"` succeeds
2. the selected endpoint is still a real remote endpoint, so the request does not hard-fail

   - `routingDiagnostics.routingMode.aliasMode = "controller"`
   - `routingDiagnostics.controllerRouting.active = true`
   - `routingDiagnostics.controllerRouting.fallbackApplied = true`

That means the controller execution path is alive, but the parser still rejects the model's JSON shape.

## Concrete Root Cause

**Root Cause:** `/role-model-router/apps/runtime-host-bridge/src/controller-routing-contract.ts` only accepts the strict strategy vocabulary `balanced | cost | quality`. The live controller model can instead return adjacent strategy-like values such as:

- `capability_based`
- `prefer-capability`
- `remote_only`

Those values are semantically meaningful, but `normalizeStrategy()` currently treats them as fully invalid. When the controller output contains only one of those looser fields, `sanitizeControllerRoutingGuidance()` returns `null`, and `/role-model-router/apps/runtime-host-bridge/src/index.ts` marks the whole controller result as `fallbackReason: "invalid-controller-output"`.

## Why The Current Behavior Is Wrong

This is not a genuine invalid-output case in the live system:

1. `capability_based` and `prefer-capability` both express a capability/quality preference that the runtime can safely map to `quality`
2. `remote_only` expresses transport preference, which the runtime can safely interpret as `preferLocal: false` without requiring a new strategy enum
3. rejecting the whole payload loses useful routing intent and keeps fallback rates artificially high even though the controller is behaving coherently

## Fix Strategy

1. add a controller-output compatibility layer inside the controller-routing contract
2. normalize known adjacent strategy vocabulary into runtime-safe directives before final sanitization
3. salvage remote/local preference signals even when they arrive through the `strategy` field instead of the dedicated `preferLocal` field
4. add failing regression tests first at both the contract and live request-path level
5. rebuild and relaunch the runtime, then re-probe `controller.remote-only` to confirm the fallback rate drops
