## Root Cause

The current routing doc uses `hosted web search` in a way that reads as if it were a
provider-generic capability. That is not what the code implements.

The live runtime currently distinguishes only two execution surfaces:

1. ordinary function tools
2. hosted tools expressed through the normalized OpenAI Responses contract

In code today:

- `/role-model-router/packages/adapter-execution/src/index.ts` models hosted tools only
  as raw request payloads
- `/role-model-router/packages/provider-openai/src/index.ts` preserves hosted tools only
  on the OpenAI Responses path and rejects them on chat-completions
- `/role-model-router/apps/runtime-host-bridge/src/index.ts` gates hosted
  `web_search` through the OpenAI Codex Subscription model matrix

The doc drift happened because provider facts and runtime-contract facts were blended:

- Kimi does support provider-native official tools including web search, rethink, and
  code runner
- DeepSeek does support function tools and documents native web search in the Claude
  Code integration
- but neither provider is currently modeled in this repo as supporting the normalized
  OpenAI Responses hosted-tool contract `tools: [{ type: "web_search" }]`

So the bug is documentation ambiguity, not a newly discovered provider outage.

## Consequence

Operators can incorrectly infer one of two wrong things:

1. only OpenAI models are capable of web search at all
2. Kimi and DeepSeek should already accept the same hosted-tool request shape used for
   OpenAI Responses

Both are false. The missing distinction is:

- provider capability exists
- runtime metadata models that capability in some way
- runtime request-shape support is wired for that capability on a specific transport
