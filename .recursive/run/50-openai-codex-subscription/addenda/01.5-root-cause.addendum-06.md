Scope note: This addendum covers the live post-restart routing collapse where `controller.remote-only` keeps selecting DeepSeek Flash because controller guidance times out and routing falls back to raw observed-data scoring.

## Live Failure Shape

Consumer requests sent to `http://127.0.0.1:3461/v1/chat/completions` through the `controller.remote-only` alias showed:

1. all requests route to `deepseek/deepseek-v4-flash`
2. Kimi is healthy and eligible again after the OAuth probe fix
3. recorded request artifacts show:
   - `routingDiagnostics.controllerRouting.active = true`
   - `routingDiagnostics.controllerRouting.fallbackApplied = true`
   - `routingDiagnostics.controllerRouting.fallbackReason = "controller-timeout"`

That means the alias matrix is present and the multi-provider candidate pool exists, but controller arbitration is never landing in time.

## Concrete Root Cause

The runtime currently uses an unrealistically small controller timeout budget in two places:

- `/role-model-router/apps/runtime-host-bridge/src/unified-runtime-config.ts`
  - `DEFAULT_UNIFIED_RUNTIME_CONTROLLER_CONFIG.timeoutMs = 1500`
- `/role-model-router/apps/runtime-host-bridge/src/index.ts`
  - persisted controller assignment fallback injects `timeoutMs: 1500`

The live remote controller path takes longer than `1500ms` under realistic runtime conditions, so every intelligent-routing request falls back before controller guidance arrives. Once fallback occurs, observed performance metrics strongly favor DeepSeek Flash over Kimi, so coding traffic never reaches the Moonshot endpoint.

## Reproduction Evidence

Live request inspection after sending alias traffic to port `3461` shows:

- controller routing is active
- no controller directives are accepted
- fallback reason is consistently `controller-timeout`

The new regression test in `/role-model-router/apps/runtime-host-bridge/test/index.test.ts` reproduces the same issue with a simulated `2000ms` remote controller response and no explicit `timeout_ms` in config. It currently fails because the default timeout expires before controller guidance is parsed.

## Root Cause Summary

**Root Cause:** the default intelligent-routing controller timeout is too low and is duplicated in both config normalization and runtime fallback assignment, causing live controller arbitration to time out and collapse routing onto fallback score winners.

**Location:** `/role-model-router/apps/runtime-host-bridge/src/unified-runtime-config.ts` and `/role-model-router/apps/runtime-host-bridge/src/index.ts`.

**Impact:** `controller.*` aliases cannot reliably arbitrate across providers after restart; routing silently degrades to observed-data fallback and over-selects the fastest endpoint instead of honoring controller intent.

## Fix Strategy

1. define a shared controller timeout default suitable for realistic remote latency
2. use that shared default in config normalization and persisted-controller fallback injection
3. keep explicit per-config `timeout_ms` overrides unchanged
4. prove the fix with RED/GREEN regression coverage and then re-run live alias traffic against the rebuilt runtime

## Test Requirement

This fix requires:

- the new default-timeout controller regression test to fail before the change and pass after it
- regression coverage showing explicit `timeout_ms` values still win over the default
- live consumer validation against the rebuilt runtime showing controller-guided multi-provider routing works again
