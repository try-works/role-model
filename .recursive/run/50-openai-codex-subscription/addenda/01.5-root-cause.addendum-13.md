## Data Flow Trace

### Root Cause A: live controller fallback is caused by prompt-shape sensitivity, not just parser incompatibility

Current live controller assignment:

- `endpointId = deepseek.personal.deepseek-api-key.global.deepseek-v4-flash`
- `modelId = deepseek/deepseek-v4-flash`

Direct exact-model controller replay proved two different behaviors with the same runtime contract:

1. simpler coding prompts returned valid JSON such as:
   - `requestedRoleId = "coder.patch"`
   - `taskType = "code.edit"`
   - `requiredCapabilities = ["code.edit"]`
   - `preferredCapabilities = ["reasoning.multi_step"]`
   - optional `strategy = "balanced"`
   - sanitizer accepted these outputs
2. a harder controller prompt with `toolCount = 2` returned:
   - `finishReason = "length"`
   - empty visible `message.content`
   - sanitizer result `null`

That means the live `invalid-controller-output` failure is not only a parser-shape problem. The current verbose controller prompt can drive the flash controller into an empty visible completion on harder requests, which the runtime then records as invalid guidance.

### Root Cause B: the difficulty heuristic underweights hard single-turn code-change requests in ask-mode

The current heuristic path:

1. uses ask-mode text for declared-tools/no-tool-use requests
2. computes:
   - `instructionConstraintCount`
   - `decompositionKeywordCount`
   - `codeOrSchemaBurden`
   - context/history/tool counts
3. maps score:
   - `>= 7` -> `hard`
   - `>= 3` -> `medium`

The live harder coding probes stayed at `medium` because they were:

1. single-turn or low-history asks
2. no active tool-turn usage
3. code-heavy, but not scoring enough with the current keyword buckets to cross the `hard` threshold

So the runtime is structurally biased toward `medium/balanced` for complex code-debug or patch-planning prompts that humans would already consider hard enough to prefer quality routing.

So the remaining controller gap is different from the earlier contract-compat issue. The parser can accept compatible strategy aliases when visible JSON exists; the failure now occurs when the controller endpoint emits no visible JSON payload at all for a harder prompt.

Likewise, the difficulty issue is not an endpoint-health problem:

1. all four remote endpoints are healthy and executable
2. general balanced aliases already moved to `deepseek-v4-pro` once observed profiles were refreshed
3. only the harder code-oriented difficulty path remains insufficiently discriminating

## Root Cause Summary

1. the live controller path still falls back because the verbose controller prompt can cause `deepseek-v4-flash` to return an empty visible completion on harder requests, which sanitizes to `null`
2. the difficulty heuristic still under-classifies hard code-change requests because the current ask-mode scoring does not award enough weight to high-risk single-turn code-debug or patch-planning prompts
