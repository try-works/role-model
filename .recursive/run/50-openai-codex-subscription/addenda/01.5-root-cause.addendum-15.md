## Data Flow Trace

`routeRequest()` sorts candidates with this rule:

1. compare `total_score`
2. if the delta is within `SCORE_TIE_EPSILON`
3. fall back to `compareTieBreak()` using:
   - `quality`
   - `latency_ms`
   - `reliability`
   - `endpoint_id`

The key constant is:

- `SCORE_TIE_EPSILON = 0.01`

For the live post-warm request:

- `deepseek-v4-pro total_score = 0.8252557768`
- `kimi-k2.7-code total_score = 0.8204552493`
- delta = `0.0048005275`

That delta is smaller than the configured epsilon, so the router intentionally treats the candidates as tied and lets the tie-break path decide. Kimi then wins on higher `quality`.

## Root Cause Summary

The live routing behavior is correct, but the operator diagnostics are incomplete:

1. the core router does not explicitly record when a score-tie epsilon caused the tie-break comparator to decide the winner
2. runtime request detail does not surface the tie-break-vs-total-score decision mode, so Observe can look self-contradictory even when the router followed its intended rules

## Fix Strategy

1. add RED regressions proving score-near-tie routing emits explicit tie-break diagnostics
2. add a new router selection reason for tie-break wins within the score epsilon
3. surface selection diagnostics in runtime request detail so Observe can show:
   - comparator mode
   - score delta
   - configured tie epsilon
4. rebuild and rerun the live `controller.remote-only` warmup sequence on `:3462` to confirm the selected endpoint stays the same but the emitted reasoning becomes truthful
