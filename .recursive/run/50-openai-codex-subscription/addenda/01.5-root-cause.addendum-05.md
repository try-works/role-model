Scope note: This addendum covers the post-restart multi-provider routing regression uncovered during live consumer validation, where Kimi is excluded from `controller.remote-only` because remote health probes leave its OAuth-backed endpoint in a stale degraded state.

## Live Failure Shape

Consumer validation against the rebuilt runtime on port `3461` produced three important signals:

1. direct runtime requests to `moonshot/kimi-k2.7-code` succeed
2. the same runtime reports the Kimi endpoint as `degraded`
3. `controller.remote-only` request artifacts exclude the Kimi endpoint before scoring with:
   - `POLICY_DENY_ENDPOINT`
   - `allow_endpoints` containing only DeepSeek and OpenAI endpoints

The exclusion is not coming from controller scoring itself. It happens earlier when alias candidate pools are built from routable inventory, and routable inventory treats `degraded` remote endpoints as unroutable.

## Concrete Root Cause

The stale degraded state originates in the remote health probe authorization path:

- `/role-model-router/apps/runtime-host-bridge/src/index.ts`
  - `resolveProbeAuthorization`
- `/role-model-router/apps/runtime-host-bridge/src/remote-health-probe.ts`
  - `probeTarget`

`resolveProbeAuthorization` currently reads the persisted OAuth `access_token` directly from disk and returns it unchanged. It does not:

- pre-refresh expired OAuth credentials using the same execution helper path
- retry remote health probes after `401` / `403` by refreshing the OAuth access token

That behavior diverges from live execution, which already retries provider requests after `401` / `403` by calling `refreshOauthAccessToken`.

## Reproduction Evidence

Using the persisted Moonshot OAuth credential in the runtime state root:

- `https://api.moonshot.ai/v1/models` returns `401`
- `https://api.moonshot.ai/v1/chat/completions` also returns `401`

But routed execution through the runtime still succeeds because the live execution path refreshes OAuth on auth failure. The remote health probe path does not, so it records a false degraded result and leaves the endpoint out of alias inventory.

## Root Cause Summary

**Root Cause:** remote health probes use stale persisted OAuth access tokens without the refresh-and-retry behavior used by live execution, causing valid OAuth-backed remote endpoints to remain falsely degraded after restart.

**Location:** primarily `/role-model-router/apps/runtime-host-bridge/src/index.ts` and `/role-model-router/apps/runtime-host-bridge/src/remote-health-probe.ts`.

**Impact:** healthy Moonshot/Kimi execution is hidden from routable inventory, so mixed remote aliases such as `controller.remote-only` cannot route coding traffic to Kimi even though the provider is operational.

## Fix Strategy

Align remote health probes with live execution semantics:

1. resolve probe authorization through the same credential resolution path used by execution so expired OAuth tokens can refresh pre-probe
2. on `401` / `403`, refresh OAuth authorization once and retry the `/models` probe before marking the endpoint degraded
3. add regression tests that prove OAuth-backed remote probes recover from stale access tokens and surface `healthy` state afterward

## Test Requirement

This fix requires RED/GREEN coverage for:

- probe retry after initial auth failure with refreshed authorization
- probe still returning `auth` when refreshed authorization also fails
- runtime-host bridge preserving Kimi in healthy routable inventory after a successful auth-refresh probe path
