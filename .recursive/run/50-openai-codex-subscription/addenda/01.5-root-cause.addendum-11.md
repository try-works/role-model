Scope note: This addendum covers the remaining live `controller.remote-only` timeout plus the routing-alias matrix behavior that is still too narrow and too permissive.

## Live Failure Shape After The Controller Budget Fix

After the controller-response budget patch landed and the runtime was rebuilt/relaunched, fresh live `controller.remote-only` requests no longer failed with `invalid-controller-output`. They now fail with:

1. `routingDiagnostics.controllerRouting.active = true`
2. `routingDiagnostics.controllerRouting.fallbackApplied = true`
3. `routingDiagnostics.controllerRouting.fallbackReason = "controller-timeout"`

That narrows the next live issue to timeout budget, not parser compatibility or response truncation.

## Concrete Root Causes

### Root Cause A: persisted controller fallback still uses a 5000 ms timeout

When the runtime does not have an explicit controller block in the current config and instead uses the persisted controller assignment, `/role-model-router/apps/runtime-host-bridge/src/index.ts` synthesizes a controller config with:

- `timeoutMs: DEFAULT_UNIFIED_RUNTIME_CONTROLLER_TIMEOUT_MS`

That shared default currently comes from `/role-model-router/apps/runtime-host-bridge/src/unified-runtime-config.ts` and is still `5000`.

The live controller request now produces valid JSON when given enough output budget, but the end-to-end controller turn can still exceed 5000 ms. The bridge then falls back with `controller-timeout` before it can accept the valid directives.

### Root Cause B: canonical alias generation still collapses to one primary alias

The runtime still has two single-alias materialization seams:

1. `canonicalizeUnifiedRuntimeRoutingAliases()` in `unified-runtime-config.ts`
2. `materializePrimaryRoutingAlias()` in `index.ts`

Both are built around one primary alias for the *current* strategy/execution-mode pair. That means the runtime does not persist the full canonical alias matrix across strategy families and execution modes.

### Root Cause C: alias resolution is still broad inventory fallback, not strict matrix resolution

`resolveAliasAllowEndpoints()` in `routable-inventory.ts` currently starts from `inventory.entries` for every alias mode and then adds any hint-model matches. That means an alias effectively widens to the whole routable inventory instead of resolving only the endpoints that belong to its canonical matrix slice.

This is wrong for:

1. execution-mode-scoped aliases such as `controller.remote-only`
2. matrix correctness
3. controller candidate-pool construction
4. regression detection when alias/model inventory drifts

## Why The Current Behavior Is Wrong

The user expectation is that the runtime exposes a durable alias matrix for routing strategy and execution-mode combinations, and that each alias resolves to the exact endpoint slice implied by that configuration.

Today the runtime instead:

1. persists only one canonical primary alias at a time
2. allows alias resolution to broaden to the entire effective inventory
3. feeds controller routing with that overly generic alias pool
4. times out persisted controller assignments too aggressively for the now-longer valid controller response

That produces confusing operator behavior even after the parser and token-budget fixes landed.

  - `resolveAliasAllowEndpoints()` therefore widens most aliases to the entire effective inventory

## Fix Strategy

1. add RED regressions for:
   - persisted-controller default timeout budget
   - full canonical alias-matrix persistence
   - strict alias resolution against matrix slices
   - execution-mode-scoped controller candidate pools
2. raise or make configurable the default persisted-controller timeout
3. replace single-primary-alias materialization with full canonical matrix generation while preserving non-primary custom aliases
4. make alias resolution strict to alias model membership instead of broad inventory fallback
5. verify the controller live path again after rebuild/relaunch
