Scope note: This addendum supersedes the earlier transport-limitation assumption for GPT-5.4 on `Codex Subscription`. The issue is not that the underlying OpenAI/Codex transport lacks web search or tool use; the issue is that the runtime-host bridge strips those capabilities before the request reaches Codex app-server.

## External Capability Verification

Official OpenAI docs confirm:
- GPT-5.4 supports tools including function calling, web search, file search, and computer use.
- Web search is part of the Responses API tool surface.
- Codex app-server supports:
  - built-in web-search items (`item.type = "webSearch"`)
  - experimental request-scoped dynamic tools via `thread/start.dynamicTools`
  - server-request/response execution for those dynamic tools through `item/tool/call`

## Live Probe Evidence

### Probe A: direct Codex app-server web search

Using a temporary `CODEX_HOME` seeded from the local `~/.codex/auth.json` and `config.toml`, a direct `app-server` turn with model `gpt-5.4` and a stock-price prompt succeeded.

Observed result:

- success reproduced under `sandboxPolicy.type = "readOnly"`

### Probe B: direct Codex app-server dynamic function tool

Using `initialize.params.capabilities.experimentalApi = true` and `thread/start.dynamicTools`, a direct `app-server` turn invoked a custom tool:
- request observed: `item/tool/call`

- final answer incorporated the tool result: `Endpoint alpha is healthy.`

Therefore the transport also supports request-scoped function tools when the host exposes them correctly.

## Code-Level Root Cause

The bridge currently removes Codex app-server semantics in two places:

1. `/role-model-router/apps/runtime-host-bridge/src/index.ts`
   - `buildCodexTurnPrompt(...)`
   - rewrites the OpenAI-compatible request into a plain text prompt
   - includes the hard restriction:
     - `Do not run commands, modify files, access the network, or ask for approvals.`

2. `/role-model-router/apps/runtime-host-bridge/src/index.ts`
   - `createSystemCodexExecutionAdapter()`
   - starts `thread/start` without exposing request-scoped `dynamicTools`
   - starts `turn/start` with only the flattened text prompt instead of faithfully preserving tool-capable request semantics

Separately, the Responses request parser still rejects hosted tools by construction:

3. `/role-model-router/apps/runtime-host-bridge/src/index.ts`
   - `toResponsesToolDefinition(...)`
   - throws unless the tool is an OpenAI function tool

## Root Cause Summary

**Root Cause:** The runtime-host bridge downgrades GPT-5.4 / Codex Subscription requests from a real Codex app-server turn into a prompt-only shim, and the request parser rejects hosted OpenAI tools before execution.

**Location:** `/role-model-router/apps/runtime-host-bridge/src/index.ts`

**Detailed Explanation:** GPT-5.4 on the underlying Codex transport can already web-search and execute dynamic function tools on this machine. The role-model runtime loses that capability because it rewrites requests into a single text instruction that forbids network/tool behavior, never provisions `dynamicTools`, and only accepts function-style tool definitions at the request-parser layer. The transport is capable; the bridge is lossy.

**Fix Strategy:** Replace the prompt-only Codex shim with a transport-faithful app-server bridge:
- allow hosted Codex web-search behavior for GPT-5.4 turns
- provision request-scoped dynamic function tools
- stop advertising or suppressing capabilities based on the current shim limitation

**Test Plan:** Add RED/GREEN coverage for:
- hosted `web_search` request acceptance
- Codex app-server dynamic tool provisioning from request tools
- live bridge execution of a request-scoped tool call
- plain stock-price query routed to Codex Subscription without the network-denied refusal
