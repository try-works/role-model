Scope note: This addendum records the invalid `craft-ask` routing-family carryover that remains in the runtime strategy matrix, alias generation, regression suite, and routing architecture documentation.

## Error Analysis

The current runtime still treats `craft-ask` as if it were a first-class routing strategy family:

1. `unified-runtime-config.ts` includes `craft-ask` in the primary alias prefixes
2. `index.ts` includes `craft-ask` in the canonical routing-alias strategy matrix
3. focused regression suites assert `craft-ask.decision-only`, `craft-ask.hybrid`, `craft-ask.local-only`, and `craft-ask.remote-only`
4. `docs/architecture/09-runtime-routing-strategy-interactions.md` documents `craft-ask` as a legitimate canonical alias family

That is inconsistent with the current operator contract. The user-facing routing-strategy surface is supposed to expose only the supported routing families and their execution-mode slices. `craft-ask` is not one of those valid routing families.

## Concrete Root Cause

`craft-ask` originated as a request-shaping heuristic for Craft ask-mode behavior, but parts of the runtime later promoted it into the persisted routing-strategy and canonical-alias machinery.

That promotion is now wrong in three ways:

1. it creates unsupported persisted strategy values
2. it expands the canonical alias matrix with unsupported alias ids
3. it teaches the docs and regression suite that `craft-ask` is part of the routing control plane instead of a lower-level request-classification concern

## Correct Boundary

The bounded correction is:

1. remove `craft-ask` from persisted routing-strategy normalization where it behaves like a valid family
2. remove `craft-ask.*` from canonical alias generation and primary-alias recognition
3. update tests and routing docs so only supported routing families remain in the matrix
4. preserve any still-valid Craft ask-mode request heuristics only as request analysis, not as a routing strategy or alias namespace

## Why This Must Be Fixed In Run 50

Run 50 already owns the canonical alias matrix, routing-strategy interactions doc, and live routing truthfulness work. Leaving `craft-ask` in the matrix would keep the repaired routing control plane internally inconsistent even if the live runtime happened not to select those aliases during manual QA.
