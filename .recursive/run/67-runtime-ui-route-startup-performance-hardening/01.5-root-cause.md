## Root Cause Summary

Root Cause:

- the route-startup problem was caused by legacy broad bootstrap helpers and parity assumptions that survived after run 66 fixed only the providers page.

Location:

- `/role-model-router/apps/runtime-ui/app/lib/runtime-api.ts`
- `/role-model-router/apps/runtime-ui/app/routes/control-models.tsx`
- the remaining `P0` route files under `/role-model-router/apps/runtime-ui/app/routes/`
- `/role-model-router/apps/runtime-host-bridge/src/cli.ts`
- `/role-model-router/apps/runtime-host-bridge/scripts/start.ts`
- `/role-model-router/apps/runtime-host-bridge/scripts/prod-launcher.ts`
- `/role-model-router/apps/runtime-host-bridge/src/validate-packaging.ts`

Explanation:

- the UI still used a route-agnostic snapshot on pages that only needed narrower first-paint data, the non-QA startup constructors lagged the QA helper on latest-ids wiring, and packaged validation still over-trusted `/healthz`

Fix Approach:

- narrow `/app/models` first paint and defer request evidence
- remove `fetchRuntimeSnapshot()` from the targeted `P0` family
- wire latest-ids through non-QA startup
- strengthen packaged validation with a runtime-summary readiness wait

Test Strategy:

- strict RED-first route, host-bridge, and packaging tests
- broader validator/browser/package reruns
- rebuilt packaged-runtime proof on persisted standalone state
