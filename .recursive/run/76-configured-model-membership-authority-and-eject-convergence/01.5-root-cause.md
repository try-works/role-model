## Error Analysis

The operator-visible error is a successful eject followed by the model reappearing. There is no thrown stack trace because the mutation returns `{success:true}`. The semantic error is visible in state:

- before: target is in `allowedModels`, endpoint rows, and remote activations;
- DELETE: endpoint row is deleted and account update is attempted;
- after the method's own rebuild: target is again in `allowedModels`, endpoint is absent, activation remains;
- after restart bootstrap: the surviving activation may recreate the endpoint too.

**Key insight:** the failure is not stale UI cache. The backend rewrites authoritative-looking account state from derived evidence during the same request.

## Data Flow Trace

### RC1 - activation-driven immediate resurrection

1. `activateRuntimeEndpoint()` writes an endpoint and upserts a remote activation.
2. `removeProviderAccountModel()` deletes the endpoint but not the activation.
3. It writes the filtered account and calls `rebuildCurrentState()`.
4. `readCurrentAccounts()` invokes `repairPersistedProviderAccountsFromRuntimeState()`.
5. The repair reads the surviving activation into `requiredModelsByAccountId`.
6. It unions that model into `allowedModels` and persists the repaired account.
7. The next read/UI refresh shows the model again.
8. On restart, the endpoints stage can recreate the missing endpoint from the same activation.

### RC2 - endpoint-evidence legacy resurrection

1. Legacy or partially mutated state contains an account that excludes a model while a matching endpoint row remains.
2. Account repair treats the endpoint as a required model.
3. The endpoint model is unioned back into account membership.
4. Existing restart coverage named as drift repair currently codifies this positive reconstruction.

### RC3 - runtime-config reapply resurrection

1. YAML LiteLLM `modelMappings` generate `*.litellm` account `allowedModels`.
2. Manual/persisted and config-generated memberships are unioned.
3. Config apply deletes and re-persists config accounts from mappings.
4. Startup invokes config apply again.
5. A SQLite-only eject cannot survive unless YAML is changed or a higher-precedence negative membership decision is applied.

### RC4 - partial mutation risk

1. Current eject deletes endpoint rows first.
2. It then validates the surviving account.
3. If validation fails, the account remains unchanged while endpoints are already gone.
4. JSON and YAML writes add further stores that require explicit transaction/compensation semantics.

### RC5 - missing conflict ownership

1. Controller, classifier, custom aliases, and LiteLLM mappings may reference the target.
2. No shared reference descriptor classifies safe derived references versus explicit user-authored references.
3. Eject cannot block before mutation or return deterministic conflict details.

## Root Cause Summary

**Root Cause:** configured membership has no single precedence and mutation contract; positive recovery/config evidence can recreate membership after a negative eject, while the eject itself is an incomplete, non-transactional cross-store mutation.

**Locations:** `src/index.ts` account repair (`15522-15644`), config account generation/apply (`5065-5150`, `5895-5923`, `17362-17455`), eject (`22226-22292`), bootstrap activation replay (`24106-24151`), plus reference types in `src/unified-runtime-config.ts`.

**Fix Strategy:** Phase 2 must select one canonical account-plus-model membership contract, make all reads and positive/negative mutations honor it, classify other surfaces as derived or explicit references, preflight conflicts, converge derived stores with rollback semantics, and sanitize legacy evidence from authority outward.

**Test Plan:** strict RED tests must cover immediate activation resurrection, stale endpoint restart, runtime-config reapply, sibling/last/repeat eject, conflict preflight before mutation, legacy sanitization, sibling account isolation, still-configured preservation, and local wildcard negative control.

## Root Causes

1. `RC1`: activation evidence survives eject and is promoted back into account membership during the same rebuild.
2. `RC2`: stale endpoint evidence is also promoted into membership.
3. `RC3`: runtime-config mappings regenerate config-backed membership on apply/startup.
4. `RC4`: eject ordering lacks atomic or compensating cross-store semantics.
5. `RC5`: no generic ownership-aware reference preflight exists.

## Corrective Direction

1. Define the canonical membership key and persistence/precedence matrix in Phase 2 without assuming SQLite or YAML prematurely.
2. Make add/eject/config apply/rebuild/restart/migration use the same membership service or helper contract.
3. Make endpoints, activations, bindings, lifecycle summaries, health, and UI projections derived from membership.
4. Add ownership-aware reference descriptors for auto-prunable derived state and blocking explicit references.
5. Validate and preflight before writes; use SQLite transaction support where possible and explicit snapshots/compensation across JSON/YAML.
6. Emit structured mutation and sanitization diagnostics.
