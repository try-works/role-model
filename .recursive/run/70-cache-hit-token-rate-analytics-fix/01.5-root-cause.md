## Error Analysis

This run does not start from a thrown runtime exception. It starts from a deterministic analytics-contract error:

- the backend reports `cacheHitTokenRate` near half of the true value whenever cached tokens are already included in `inputTokens`
- the owning regression encodes that same wrong value, so the bug is currently protected rather than exposed

Observed failure summary:

- supported cached-token rows currently carry truthful total input and cached-subset facts
- the analytics formula then adds cached tokens back into the denominator as if they were extra prompt tokens
- the UI chart simply renders the backend metric and therefore inherits the mathematically wrong result

**Key Insight:** the defect is not a provider-normalization problem and not a chart-rendering problem. It is a backend analytics formula defect that double-counts cached tokens after the upstream paths have already normalized them correctly.

## Pattern Analysis

**Working example:** request-level cache support already follows correct set semantics in `/role-model-router/apps/runtime-host-bridge/src/index.ts:17321-17325`, where `cacheBackedRequestRate` counts cached requests as a subset of total requests.

**Broken code:** token-level cache support in `/role-model-router/apps/runtime-host-bridge/src/index.ts:17327-17342` treats cached tokens as additive rather than subset-based.

**Key Differences:**

| Aspect | Working or intended truth | Broken state |
| --- | --- | --- |
| request subset semantics | cached requests are counted within total requests | correct |
| token subset semantics | cached prompt tokens should be counted within total input tokens | broken: cached tokens added again in denominator |
| upstream provider contract | `inputTokens` is total prompt input; `cacheReadTokens` is a separate detail field | correct across provider-openai, LiteLLM, Kimi-shaped, and bridge-owned Codex paths |
| regression floor | tests should fail if denominator double-counts cached tokens | broken: current test expects the double-counted value |

**Likely Cause:** the telemetry metric was introduced with a conceptual mismatch between "cache reads are part of prompt input" and "cache reads are an extra avoided-cost fact," then the incorrect denominator was preserved when partial-support behavior was later added.

## Root Cause Summary

**Root Cause:** the backend analytics implementation for `cacheHitTokenRate` double-counts cached tokens by adding `cacheReadTokens` back into a denominator whose `inputTokens` values already include those cached tokens.
**Location:** `/role-model-router/apps/runtime-host-bridge/src/index.ts:17327-17342`
**Detailed Explanation:** all in-scope execution paths already normalize usage as `total input tokens + separate cached-token detail`. The analytics layer should therefore compute cached-token hit rate as `sum(cacheReadTokens) / sum(inputTokens)` over supported rows. Instead, the current implementation computes `sum(cacheReadTokens) / sum(inputTokens + cacheReadTokens)`. That turns a subset relation into an additive relation and mathematically halves the reported rate on high-hit requests. The adjacent request-level metric is not affected because it already uses subset semantics correctly, and the frontend is not affected independently because it only consumes the backend-owned value.
**Fix Strategy:** Phase 2 should plan one shared analytics fix in the host-bridge metric calculation, then update the owning host-bridge regression to go RED on the corrected denominator while preserving partial-support behavior and leaving `cacheBackedRequestRate` unchanged. Cross-path protection should come from the existing provider-openai, bridge-owned Codex, Kimi-shaped, and LiteLLM normalization seams rather than from provider-specific analytics branches.
**Test Plan:** Phase 3 must start with a failing host-bridge regression that expects `0.133333` for the current seeded `120`/`16` fixture, then keep regression controls green for direct OpenAI-compatible nested cache facts, Kimi top-level cache facts, bridge-owned Codex usage shaping, and LiteLLM normalization. Phase 5 must verify the corrected metric on the rebuilt runtime through the backend query surface and an existing operator chart path.
