## Error Analysis

This run begins from a deterministic user-visible performance failure:

- `/app/remote/providers` takes more than a minute to become usable.
- The approved direction is to render the page first, then fetch only the latest `10` request ids.

Observed failure-family summary:

- UI bootstrap coupling failure:
  - the providers route blocks its initial render on `fetchRuntimeSnapshot()`.
- Shared snapshot overreach failure:
  - `fetchRuntimeSnapshot()` always includes `/api/role-model/requests`, even though the providers route does not consume `snapshot.requests`.
- Backend over-fetch failure:
  - `/api/role-model/requests` resolves through `listRecentRuntimeObservations()`, which selects `observation_json` from `runtime_observations` and parses every selected row.
- Route-specific contract gap:
  - the repo already has lighter route-specific helpers for other surfaces, but not for the providers page.
- Regression-proof failure:
  - current tests do not encode deferred providers-page loading or a latest-10 ids-only path.

**Key Insight:** the one-minute stall is not primarily a React rendering problem. The page is waiting on a shared bootstrap contract that drags a heavyweight request-history route into first render, and that backend route performs work the providers page does not need.

## Reproduction Verification

The failure is reproducible by direct code-path tracing and live timing:

1. Open `/app/remote/providers`.
2. The route `load()` waits on `Promise.all([fetchRuntimeSnapshot(), fetchRolePolicy()])`.
3. `fetchRuntimeSnapshot()` always calls `/api/role-model/requests`.
4. The page cannot set `snapshot` or apply provider selection until that promise resolves.
5. Live runtime timings show:
   - `GET /api/role-model/runtime/summary` -> about `220.35 ms`
   - `GET /api/role-model/requests` -> about `73154.97 ms`
6. The providers route does not read `snapshot.requests`, so that delay is paid before render for data the page does not use.

**Reproducible:** Yes
**Frequency:** Deterministic in the current code and reproduced on the current live runtime

## Root Cause Summary

**Root Cause:** the providers route bootstraps through a shared snapshot helper that always blocks on `/api/role-model/requests`, and that backend request route uses the rich raw-observation table path that selects and parses `observation_json` even though the providers page only needs latest request ids later, not rich request-history during first render.
**Location:** `/role-model-router/apps/runtime-ui/app/routes/providers.tsx`, `/role-model-router/apps/runtime-ui/app/lib/runtime-api.ts`, `/role-model-router/apps/runtime-host-bridge/src/index.ts`, `/role-model-router/packages/sqlite-memory/src/index.ts`
**Detailed Explanation:** the UI route and shared runtime snapshot contract couple the providers page to request-history during first render. The backend request route then fulfills that unnecessary dependency by reading and parsing the rich raw observation payloads from `runtime_observations`. Because first render waits for the entire snapshot, the providers page inherits the latency of the wrong backend surface. The existing shell and dashboard helpers show that the repo already prefers route-specific lighter contracts when a route does not need the full shared data set.
**Fix Strategy:** Phase 2 must plan work in this order:
1. break the providers route's first-render dependency on request history
2. introduce a providers-page-specific deferred follow-up for recent request ids
3. provide a latest-10 lightweight backend path that avoids `observation_json` reads/parsing
4. preserve the existing rich request-ledger and request-detail surfaces unchanged
5. add strict RED-first runtime-ui and backend/storage regression coverage before production changes
6. reserve rebuilt-runtime providers-page proof for later verification phases
**Test Plan:** Phase 3 must follow strict TDD:
1. RED: providers-route/runtime-api tests proving first render no longer depends on `/api/role-model/requests`
2. RED: runtime-ui tests proving a post-load latest-10 follow-up occurs
3. RED: backend/storage tests proving the lightweight latest-10 path avoids `observation_json` parsing and preserves ordering
4. GREEN: minimal implementation in the route, runtime-api, host-bridge, and/or sqlite layer
5. GREEN: rerun focused runtime-ui and backend/storage suites
6. GREEN: carry the verified route into validator/browser proof and rebuilt-runtime QA later
