## Root cause statement

## Error Analysis

The observable error is not a crash but a silent no-op: saving `quality`, `latency`, `cost` or a custom profile
changes nothing about how candidates are ranked, and the decision reports a strategy-shaped label that is in fact
the routing *mode* or the raw config string (`index.ts:25442-25445`, `:25556-25559`). The failure class is
"configured value has no consumer", not "consumer computes the wrong value".

## Reproduction Verification

- `git diff --name-only ca5c2126ca566086cfbe8f83cfdf339aba0879ff` shows no product change, so the behaviour is
  the baseline's.
- `runtime-host-bridge/src/index.ts:2089` returns `strategy: "balanced"` whenever difficulty routing is inactive,
  and `:10411`/`:10636` assign that value to the routing request; there is no other producer.
- `packages/core/src/router.ts:183-219` contains four weight tables that are reachable only from a strategy value
  the bridge never emits, except `balanced`, `cost` and `quality` via the difficulty buckets.
- Reading `routing-latency-policy.ts:42`, `:55` confirms the independent latency gap (2 000 ms, bounds 3..1000)
  so the two defects are not conflated.

## Recent Changes Analysis

- Run 01 (`01-protocol-routing-obs`) canonicalised the four strategies and implemented the weight tables and the
  `toPolicyStrategy` alias mapping in the core scorer.
- Runs 15/16 added the free-form `routing.strategy` string to the unified runtime config; nothing consumed it.
- `654fa997` ("fix: land runtime router and packaging follow-ups") wired that string into mode resolution and
  alias naming to make the operator page work, and introduced the synonym normalizers, including `latency-first`
  swept in from a UI chart fixture.
- Run 101 landed the Effect workspace wrapper and the queue path; it did not touch the scoring path.

## Data Flow Trace

1. `routing.strategy` is parsed (`unified-runtime-config.ts:1464-1492`) and persisted verbatim.
2. `normalizeConfiguredRoutingMode` (`index.ts:5597-5623`) collapses ten spellings into four *modes*; the scoring
   intent is discarded here.
3. `resolveEffectiveRoutingMode` (`index.ts:9497-9511`) yields the planner mode for the request.
4. `maybeApplyDifficultyRouting` (`index.ts:2065`) returns `strategy: "balanced"` at `:2089` when difficulty is
   inactive, or a bucket-derived `cost`/`quality`/`balanced` when it is active.
5. `maybeApplyControllerRouting` (`index.ts:2232`) may replace that value with a validated directive.
6. `mapChatCompletionsRequest` / `mapResponsesRequest` (`:10411`, `:10636`) assign it to
   `RoutingRequest.strategy`, which the scorer at `packages/core/src/router.ts` consumes.
   **Break point**: step 2 discards the scoring intent and step 4 never consults the config, so the saved strategy
   can never influence step 6.

## Pattern Analysis

The same value is decoded by three hand-written switches plus a fourth copy of the weights in the core, so each
layer can accept, ignore or mislabel a value without another failing - the duplication pattern that also produced
the `latency-first` synonym. The readback path (label from mode, fall back to the raw string) is a second instance
of the same anti-pattern: presentation re-deriving a value instead of reading the resolved result.

## Hypothesis Testing

- *Hypothesis: the strategy reaches the scorer but the weights are wrong.* Disproved - `STRATEGY_WEIGHTS` is
  correct and tested; the request never carries anything but `balanced`/bucket values.
- *Hypothesis: the config is not persisted.* Disproved - the value round-trips through the API and the YAML file.
- *Hypothesis: the UI is the only defect.* Disproved - the UI merely surfaces the same mode/raw-string value that
  the runtime produces.
- *Hypothesis: the alias layer overrides the strategy.* Confirmed in part - the alias `mode` is the only thing the
  config value actually drives, so the alias layer is where the intent is consumed and lost.

## Root Cause Summary

The saved scoring strategy has no consumer because the config string was retro-fitted as a mode and alias label
while the scoring path was already hard-wired to the difficulty result; the missing mapping was never asserted by a
test, and the vocabulary's duplication made the omission invisible.

The scoring strategies are inert because the persisted `routing.strategy` string was retro-fitted as a
**mode and alias label** while the scoring path had already been hard-wired to the difficulty result. Nothing in
the runtime maps the configured strategy onto `RoutingRequest.strategy`, and no test asserts that it should.

Three compounding causes:

1. **The configuration surface and the scoring surface were designed independently.** The canonical four-value
   strategy vocabulary and its weight tables were specified and implemented in run 01 for the *core scorer*
   (`packages/core/src/router.ts:183-219`, `toPolicyStrategy` at `:374-390`), while the runtime config gained a
   free-form `routing.strategy` string in run 15/16 that nothing consumed. The May 24 runtime follow-up
   (`654fa997`) then wired that string into **mode** resolution and alias naming (`normalizeConfiguredRoutingMode`,
   `normalizeRoutingStrategyForAlias`) to make the operator page work, which is where "strategy" became a mode
   label. The bridge has never set `RoutingRequest.strategy` from config: it is `difficultyRouting.strategy`
   (`index.ts:10411`, `:10636`), which is `"balanced"` outside difficulty/hybrid (`:2089`) and only
   `cost | quality | balanced` inside it (`:1966-1977`).
2. **The mapping that would have connected them was never tested.** The design document's own checkpoint -
   "is `policy_snapshot.strategy` the mode I intended to save?" - has no assertion anywhere; the four P0 cases
   that would catch it (`R11`) do not exist. The existing latency test encodes the old defaults, so the suite
   actively pins the current behaviour instead of the intended one.
3. **The vocabulary was duplicated instead of owned.** Four hand-written copies exist (the two bridge switches,
   the UI normalizer, and the core weight table), so a value can be accepted by one, ignored by another, and
   dropped by the third without any single place failing. Legacy synonyms were then swept in from a UI chart
   fixture (`latency-first` in `packages/ui/src/observe-routing-specimens.tsx`) rather than designed.

## Why it survived

- The operator-visible label looked plausible: the decisions surface showed a strategy-shaped string
  (`index.ts:25442-25445`, `:25556-25559`), so review had no reason to doubt it.
- CI proves the suites pass, and the suites encoded the old behaviour; no test expressed the intended contract.
- The docs described the three-axis model (`docs-site` router pages) while the code only implemented two, so
  intent and implementation drifted without a failing check.

## Blast radius

- `R1`-`R4` and `R7`-`R10` are all downstream of this cause: the split, the precedence ladder, the provenance,
  the controller interaction, the posture blocks and the single vocabulary owner only make sense once the
  saved strategy actually reaches the scorer.
- `R5`/`R6` (postures) and `R11`/`R12` (TDD, live QA) inherit it: postures that carry a strategy are meaningless
  until the strategy is real, and the QA matrix must observe the effective strategy rather than a label.
- Not caused by this defect: the measured-latency override's wrong metric/defaults (`R7`) and the missing UI
  surfaces (`R8`) are independent gaps, though they share the same repair phase.

## Fix direction (input to Phase 2)

1. One owner for the vocabulary and weights, with exhaustive matching so a new value fails to compile where it
   is unhandled.
2. A config schema that states the mode/scoring/pin/weights contract and normalizes legacy spellings on write.
3. A resolver that applies the documented precedence (`request intent > controller > difficulty > operator >
   balanced`) and feeds the result into `RoutingRequest.strategy`.
4. Provenance on the decision (`strategy_source`, weights digest) so the original bug class is observable.
5. Tests first for the mapping, not just the UI: the P0 cases in the design document's section 10.1.
