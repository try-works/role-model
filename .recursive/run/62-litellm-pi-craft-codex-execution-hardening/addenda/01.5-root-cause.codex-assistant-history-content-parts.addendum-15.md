# Addendum 15 Root Cause: Codex Responses Assistant History Content Parts

## Trigger

Pi multi-turn chat through `difficulty.remote-only` reached the native Codex Subscription execution path and failed with:

`400 Invalid value: 'input_text'. Supported values are: 'output_text' and 'refusal'.`

The user-visible request was not a fresh single-turn prompt. It included previous assistant history replayed by Pi into an OpenAI-compatible chat-completions request before Role Model translated that request to the Codex Responses transport.

## Prior Verification Gap

Earlier live Pi CLI verification was real Pi CLI traffic, but it primarily used fresh `--no-session` or single-prompt invocations. That proved exact endpoint and alias routing could execute, but it did not prove that Pi multi-turn history replay was translated correctly for the Codex Responses API.

This is why the earlier verification did not catch the screenshot failure.

## API Contract Evidence

The OpenAI Chat Completions API accepts assistant messages as previous model responses. Its assistant message content can be a string, text content part, or refusal content part:

- `https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create/`

The OpenAI Responses API distinguishes model input messages from previous model output messages. User/system/developer message content uses `input_text`/`input_image`/`input_file`; previous assistant output messages use output content parts, specifically `output_text` or `refusal`:

- `https://developers.openai.com/api/reference/resources/responses/methods/create/`

Therefore, the adapter cannot map every chat content part to `input_text`. It must map by semantic role.

## Fault

`role-model-router/apps/runtime-host-bridge/src/index.ts` uses a role-blind `toCodexResponsesContentPart` helper:

- strings become `{ type: "input_text", text }`
- chat `{ type: "text", text }` parts become `{ type: "input_text", text }`
- the same helper is used for both `user` and `assistant` messages

When Pi replays assistant history, Role Model emits:

```json
{
  "role": "assistant",
  "content": [{ "type": "input_text", "text": "Hey - what can I help with?" }]
}
```

That shape is invalid for a Responses assistant output message. It must be:

```json
{
  "role": "assistant",
  "content": [{ "type": "output_text", "text": "Hey - what can I help with?" }]
}
```

or a `refusal` part when the assistant history is a refusal.

## Scope Boundary

This is a Role Model runtime adapter bug. It should not be fixed by changing Pi, Craft, or provider-specific consumer behavior.

The remediation must be generic:

- role-aware chat-completions-to-Responses conversion
- no Pi-specific branches
- no model-specific branches
- no alias-specific branches
- preserve user image/file input semantics
- preserve existing native Codex streaming and telemetry behavior

## Risk

The main regression risk is over-converting all assistant content into plain text and losing refusal or future Responses-native output parts. The converter should preserve already-valid `output_text` and `refusal` assistant parts, normalize chat `text` parts, and only convert user input parts to `input_text` or `input_image`.
