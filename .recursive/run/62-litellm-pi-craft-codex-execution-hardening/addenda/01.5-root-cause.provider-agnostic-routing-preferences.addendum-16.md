## Error Analysis

- Recent `difficulty.remote-only` requests from Pi were routing to `chatgpt/gpt-5.4` and not to `deepseek/deepseek-v4-pro`.
- Live telemetry showed the runtime can route to DeepSeek for lower-difficulty alias requests, but the latest hard/tool-heavy requests all selected GPT.

- Request: `req-6d6e166b-850f-48ae-8a1b-fd1fb4a09c03`
- Requested model: `difficulty.remote-only`
- Selected model: `chatgpt/gpt-5.4`

- Capability included endpoints: DeepSeek and GPT

The important error is not that GPT wins a scored route. The error is that DeepSeek is removed before scoring even though alias resolution and capability filtering both include it.

## Data Flow Trace

Failure boundary:

1. `resolveRequestedModelPool()` resolves `difficulty.remote-only` to both configured endpoint families.
2. `filterAllowEndpointsForCapabilityRequirements()` keeps both DeepSeek and GPT for ordinary function-tool chat requests.
3. `maybeApplyDifficultyRouting()` classifies the request as hard and keeps both endpoints when both are difficulty-eligible.
4. `maybeApplyControllerRouting()` may return controller preferences, but the failing cases did not need controller output to explain the pin.
5. `resolveOpenAICodexSubscriptionRoutingModel()` detects a Codex endpoint in the pool for tool/code or non-text signals.
6. `applyOpenAICodexSubscriptionInitialPin()` rewrites `routingRequest.allowEndpoints` from the broader alias pool to `[openai.personal.openai-codex-subscription.global.gpt-5.4]`.
7. `routeRuntimeRequest()` receives a non-empty `allowEndpoints` list containing only GPT.
8. `evaluateEligibility()` in the core router marks DeepSeek ineligible with `POLICY_DENY_ENDPOINT`.

Root cause location:

- `/role-model-router/apps/runtime-host-bridge/src/index.ts`
- Functions: `resolveOpenAICodexSubscriptionRoutingModel()` and `applyOpenAICodexSubscriptionInitialPin()`

Core-router reference:

- `/role-model-router/packages/core/src/router.ts` already supports `routingModelRank` as an advisory scoring delta and does not require hard endpoint narrowing for preferences.

## Pattern Analysis

Correct provider-agnostic routing pattern:

- Alias resolution defines the candidate slice.
- Request-surface requirements narrow candidates only when endpoint metadata says a target cannot satisfy the request.
- Policy allow or deny lists are hard only when supplied by explicit policy, operator/user constraints, execution mode, role binding, health, capability, modality, or other provider-agnostic eligibility facts.
- Benchmark quality, measured quality, latency, reliability, cost, cache affinity, continuity affinity, and routing-model guidance influence scoring.
- Provider-specific code executes only after endpoint selection, inside the provider or adapter layer needed to call that endpoint.

Broken current pattern:

- A provider-specific heuristic recognizes a Codex Subscription endpoint in a mixed candidate pool.
- The host bridge converts that heuristic into a hard `allowEndpoints` policy.
- The core router never scores otherwise eligible alternatives.
- DeepSeek can only re-enter after GPT execution failure or cooldown fallback, not as a normal candidate.

The current pattern violates the corrected requirement because it makes one provider family a hidden primary for a broad request class.

## Requirement Conflict

The corrected requirement is:

- No provider-specific routing rules or preferences.
- Routing must be based on benchmark performance, measured performance, endpoint metadata, model metadata, explicit policy, and inferred hard request requirements.
- Ordinary function-tool requests should remain broadly routable when multiple endpoints declare support.
- `routingModelRank` style preference is advisory and must not become hard eligibility.

Conflicting artifacts to supersede or repair:

- `/.recursive/DECISIONS.md` entry that says Codex Subscription first-attempt pinning was added.
- `/.recursive/memory/domains/runtime-routing-and-provider-capabilities.md` line stating Codex Subscription GPT should pin first attempt for tool-bearing or non-text turns.
- `role-model-router/apps/runtime-host-bridge/test/index.test.ts` test that asserts GPT-only `allowEndpoints` for `difficulty.remote-only` tool-bearing code turns.

Compatible artifacts to preserve:

- `/docs/architecture/09-runtime-routing-strategy-interactions.md` says ordinary function tools remain broadly routable and request-surface-specific hard narrowing must be tied to actual capability/transport requirements.
- `/role-model-router/packages/core/src/router.ts` already models routing preferences as scoring deltas.
- Addenda 13 through 15 remain correct about post-routing Codex execution, streaming, and Responses conversion; they do not require provider-specific pre-routing pinning.

## Confirmed Root Cause

Root cause: the host bridge contains a provider-specific Codex Subscription pre-routing pin that rewrites an otherwise valid multi-endpoint alias pool into a GPT-only hard policy allow-list, bypassing benchmark and measured-performance scoring for ordinary tool/code requests.

This is an intended behavior in current code and tests, but it is a regression against the corrected provider-agnostic routing requirement.

## Fix Strategy

Remove provider-specific routing preference and pinning from the host bridge.

The replacement behavior must be:

- Preserve alias and capability filtering as provider-agnostic eligibility.
- Preserve provider-specific execution adapters only after endpoint selection.
- Allow ordinary function-tool and code requests to keep all compatible endpoints in the routing candidate set.
- Use benchmark and measured performance as scoring inputs.
- Use controller or routing-model preferences only as advisory scoring, never as hard `allowEndpoints` unless the user/operator explicitly supplied a hard constraint.
- Keep true hard filters for modality, capability, transport contract, role binding, endpoint health, policy, cooldown denial, and exact model requests.

## Test Strategy

Phase 3 must use strict TDD:

- Add failing tests proving the source no longer contains Codex Subscription initial-pin helpers or fallback pool logic.
- Add decision-level tests proving both endpoints remain eligible and scored when both satisfy inferred request requirements.
- Keep capability tests proving non-text and hosted-tool requirements still narrow by endpoint metadata, not provider identity.
- Verify with rebuilt runtime and real Pi/Craft clients after implementation.
