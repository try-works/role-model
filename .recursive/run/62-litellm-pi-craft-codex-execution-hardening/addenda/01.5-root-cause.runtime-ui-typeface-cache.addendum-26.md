# Addendum 26 Root Cause: Runtime UI Typeface Cache Regression

## Reproduction Verification

The user reported that the packaged app still appeared to render generic Windows typography after the startup and bundled-font fixes.

Controller verification against an isolated headless Edge profile loaded `http://127.0.0.1:3456/app` from the rebuilt package and observed:

- Inter 400 and 600 font resources returned from `/assets/fonts/*.woff2`.
- Visible overview text and controls computed `font-family: Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif`.
- IBM Plex Mono was declared and preloaded, but the overview viewport had no visible mono-token content, so the browser left that face unloaded until a mono element is rendered.

Post-fix verification against the rebuilt package observed:

- `/health` became ready in 1179 ms and `/app` returned in 36 ms.
- `/app`, `/assets/root-DZdKbiZ8.css`, and bundled font assets returned `cache-control: no-store`.
- The rebuilt release HTML references `/assets/root-DZdKbiZ8.css`; the stale `/assets/root-Dwu636HI.css` reference is gone.
- A fresh Edge profile computed the overview heading as `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` with Inter 400/600 loaded.

## Evidence Gathering

The runtime static handler serves packaged files from `staticRoot` with only `content-type` and `content-length`.

It does not emit `cache-control`, `etag`, or `last-modified`. The Windows launcher now uses the user's normal Edge profile instead of a throwaway profile, so a browser profile can keep stale local runtime UI assets across rapid package rebuilds. This matches repeated manual QA symptoms where release output changed but the visible app appeared old or typeface-inconsistent.

The launcher also opened plain `/app`. If a normal browser profile already held a stale `/app` document, it could continue to point at an old CSS asset before the browser ever observed the new response headers.

## Root Cause Summary

**Root Cause:** The packaged runtime static server does not prevent stale cached UI assets across local rebuilds, so a long-lived browser profile can display outdated CSS/JS even after the release folder is rebuilt.

**Location:** `role-model-router/apps/runtime-host-bridge/src/index.ts` static file response path.

**Fix Strategy:** Add explicit no-store local-runtime cache headers to static UI responses so every packaged runtime restart/rebuild re-fetches current HTML, CSS, JS, and font assets. Open the frontend with a launch-scoped query token so stale cached `/app` documents are bypassed on packaged launch. Keep the Inter/IBM Plex Mono design-token contract unchanged.

**Test Strategy:** Add a startup/static-server test that fetches `index.html` and an asset file and asserts `cache-control: no-store`.
