## Data Flow Trace

Current packaged path:

1. `Role-Model.bat` starts `role-model-launcher.exe`.
2. `role-model-launcher.exe` starts `role-model-runtime.exe`.
3. `role-model-runtime.exe` starts the HTTP server and prints `listening`.
4. `role-model-runtime.exe` awaits `createRuntimeBridgeBackend()`.
5. `createRuntimeBridgeBackend()` calls `initializeSqliteMemory()`.
6. `initializeSqliteMemory()` opens the live 2.2 GB SQLite DB and runs schema/backfill SQL.
7. The backfill reparses large `observation_json` values for rows whose nullable metadata can remain null by design.
8. The Node event loop is blocked, so the launcher and browser cannot receive fast health/static responses.
9. If the boot fallback exists in the packaged UI, the user sees it until the real UI can load.

Failure boundary:

- primary: `initializeSqliteMemory()` -> `initializeSchema()` repeated JSON backfill
- secondary: launcher waits for `/healthz` full readiness instead of liveness/static readiness
- secondary: runtime UI custom boot fallback obscures the real route transition

## Pattern Analysis

Correct migration pattern:

- schema column/index creation is safe on every startup
- heavyweight data backfills must be one-time, versioned, idempotent migrations
- migration completion must be recorded even when source JSON lacks optional fields so future launches do not repeat the scan
- null can be a valid final value for optional taxonomy/execution columns

Broken pattern:

- using nullable destination columns as the only backfill-completion marker
- reparsing giant JSON blobs on every launch because optional values remain null
- gating browser launch on the same readiness endpoint that requires full backend construction

## Confirmed Root Cause

Root cause: run 62 exposed startup to a repeated, non-converging SQLite JSON backfill over the runtime observation store. The backfill predicate treats null optional metadata as "not migrated", so a large historical runtime DB is reparsed at every launch. On the operator's live DB this makes `initializeSqliteMemory()` take `38618 ms` and blocks the HTTP server from responding even after it has bound. The run-62 launcher and UI changes then amplify the regression by waiting for `/healthz` and showing a visible boot fallback.

## Fix Strategy

- keep schema column/index creation in normal initialization
- move expensive observation/telemetry JSON backfills behind durable migration receipts in `migration_receipts`
- record the backfill migration as applied after one run, even when optional extracted fields remain null
- avoid selecting rows for future backfill solely because optional metadata columns are null
- keep new observation/telemetry writes populating indexed metadata columns directly so future startup does not need JSON repair
- make the launcher wait for server liveness/static availability instead of full `/healthz` backend readiness before opening the UI
- remove the runtime UI custom boot fallback and restore immediate route navigation
- verify the rebuilt package against the existing large live DB, because that is the regression trigger
