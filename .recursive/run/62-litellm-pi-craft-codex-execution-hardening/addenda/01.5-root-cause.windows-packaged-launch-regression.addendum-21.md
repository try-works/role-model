## Error Analysis

Observed symptom:

- packaged Windows runtime starts the backend quickly
- `GET /healthz` becomes ready quickly
- first real browser request to `/app` is delayed by tens of seconds
- current dirty package can also show two boot surfaces before the real runtime UI

Important distinction:

- the extra launcher boot/handoff screen is not part of committed run 62
- it comes from the current dirty working tree and rebuilt local package
- the original committed regression is older and exists even without that extra boot screen layer

## Reproduction Verification

Committed comparison:

1. run 59 launcher:
   - starts backend
   - waits for `healthz`
   - launches Windows browser through `cmd /c start msedge --app=http://127.0.0.1:3456`
2. committed run 62 launcher:
   - starts backend
   - waits for `healthz`
   - resolves a browser executable directly
   - launches Chromium as a child process with:
     - `--app=...`
     - `--new-window`
     - `--user-data-dir=<temp profile>`
   - keeps the launcher attached to that frontend child lifecycle

Current dirty tree adds another layer:

- packaged `Role-Model.bat` calls `role-model-launcher.ps1`
- the PowerShell wrapper sets `ROLE_MODEL_LAUNCHER_SKIP_FRONTEND=1`
- the wrapper polls `healthz` and then launches the browser separately
- the dirty launcher also contains an extra bootstrap/handoff server and HTML boot screen

## Data Flow Trace

### Trace 1: committed regression path

1. run 59 shell handoff:
   - `cmd /c start` hands off to the normal Windows browser shell and existing browser profile
2. committed run 62 direct-child launch:
   - browser executable is launched as a managed child
   - a dedicated temporary Chromium profile is forced through `--user-data-dir`
3. runtime evidence already gathered in this debugging cycle showed:
   - backend ready quickly
   - `/app` reachable quickly once requested
   - the long delay happens before the first real `/app` request

Root cause boundary:

- Windows browser process launch model changed from shell handoff to managed dedicated-profile child launch

### Trace 2: dirty-tree amplification

1. local package wrapper now launches `role-model-launcher.exe` through PowerShell
2. wrapper then launches the browser through another PowerShell `Start-Process`
3. dirty launcher code can also serve an intermediate boot screen and wait for handoff

This is not the original committed regression, but it amplifies the symptom and adds extra visible delay.

## Pattern Analysis

Working pattern from run 59:

- backend readiness and browser ownership are loosely coupled
- Windows shell opens the app URL using the normal browser path/profile
- launcher does not force a dedicated Chromium profile for every start

Broken pattern from committed run 62:

- packaged launcher takes ownership of Chromium startup details
- every launch forces a fresh profile
- the browser is launched as a managed child instead of a shell handoff
- this changes the time until the browser issues its first real request to `/app`

Broken pattern in current dirty tree:

- wrapper indirection plus an intermediate launcher boot screen stacks on top of the committed regression

## Confirmed Root Cause

Root cause: the committed run 62 Windows launcher replaced the run 59 shell handoff (`cmd /c start msedge --app=...`) with an attached direct Chromium launch using a dedicated temporary profile (`--user-data-dir=<temp>`). The first remediation pass removed the profile and wrapper layers, but it still launched Windows browsers through `cmd /c start "" <full-browser-path> --app=... --new-window ...`, which is not equivalent to the working run-59 shape. Live tracing showed that the runtime stayed request-idle for more than 15 seconds under that command form, while the exact run-59 token handoff produced the first `/app` request in about 1.25 seconds. The current dirty-tree PowerShell wrapper and launcher boot-screen experiments are separate later changes that amplify the symptom but are not the original regression.

## Fix Strategy

- remove the dirty wrapper/handoff launcher layer from the packaged Windows path
- remediate the committed regression at the launcher boundary by restoring the exact Windows shell-handoff command shape that issues the fast first `/app` request
- keep the runtime backend startup/readiness path intact
- keep the fix Windows-specific unless evidence later proves the same regression exists on other platforms

## Test Strategy
