## Root Cause Summary

**Root Cause:** startup and UI ownership still mix maintenance accounts, persisted endpoint rows, remote-health truth, and effective routable inventory without one canonical configured-remote contract.
**Location:** `/role-model-router/apps/runtime-host-bridge/src/index.ts`, `/role-model-router/apps/runtime-host-bridge/src/routable-inventory.ts`, `/role-model-router/apps/runtime-ui/app/lib/view-models.ts`, `/role-model-router/apps/runtime-ui/app/routes/providers.tsx`, `/role-model-router/apps/runtime-ui/app/routes/router.tsx`, `/role-model-router/apps/runtime-ui/app/routes/control-benchmark.tsx`
**Detailed Explanation:** a stale fixture-origin DeepSeek capture account can survive normal boot because placeholder cleanup only knows about fixture ids when the current boot is fixture-enabled. A local-peer maintenance account is intentionally persisted from `peers.json` but is later rendered as if it were a remote configured provider connection. Endpoint bootstrap then treats existing SQLite endpoint rows as authoritative and skips durable-intent reconciliation. Remote-health probing correctly marks three endpoints offline, and effective routable inventory correctly shrinks to one endpoint-model, but the backend continues to publish raw endpoint `status: "active"` and maintenance lifecycle records alongside that new truth. Models consumes raw `status`, providers consume maintenance accounts, router overview slices the first three raw candidates, and benchmark treats offline candidates as runnable because execution-mode eligibility is a different field. The result is one startup truth split expressed across multiple pages.
**Fix Strategy:** Phase 2 should define one canonical configured-remote inventory record and make startup authoritative only after account reconciliation, endpoint reconciliation, and health publication are combined into that contract. Provider maintenance rows should move to a separate maintenance view. Models, Router, Candidates, and Benchmark should all consume the same backend fields for health, routing eligibility, and benchmark eligibility. Router overview should summarize the canonical eligible subset rather than the first three raw candidates.

   - Why it matters: even after the backend publishes richer truth, page-local heuristics can still mislabel maintenance rows, hide the only healthy candidate, or present offline candidates as benchmark-runnable

## Corrective Direction

1. Reconcile persisted provider accounts at startup against current runtime posture, explicit provenance, current peers, current fixture mode, and configured remote intent before publishing authority.
2. Reconcile persisted endpoints against durable operator intent on every boot instead of returning early on `existingEndpoints.length > 0`.
3. Publish one canonical configured-remote inventory contract with explicit fields for:
   - maintenance versus configured execution inventory
   - lifecycle state
   - health state
   - routing eligibility
   - benchmark eligibility
   - authority state
4. Make Models, Router, Candidates, and Benchmark consume that same canonical record rather than mixed `status` and `healthStatus` fields.
5. Move provider maintenance rows into a separate, explicitly labeled maintenance section if they remain operator-visible.
6. Make router overview and benchmark selection derive from canonical eligible subsets, not raw candidate arrays or execution-mode-only filters.
7. Start Phase 3 with RED tests that expose each root cause before production code changes begin.
