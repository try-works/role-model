## Root Cause Summary

**Root Cause:** the standalone launcher can still make a stale root-level config file authoritative, and the startup pipeline still lacks a final canonical-alias rewrite after inventory reconciliation becomes authoritative.
**Location:** `/role-model-router/apps/launcher/main.go`, `/role-model-router/apps/runtime-host-bridge/src/index.ts`, and the owning tests under `/role-model-router/apps/launcher/` and `/role-model-router/apps/runtime-host-bridge/test/`
**Detailed Explanation:** the standalone launcher currently resolves its runtime-state root to `.../Role Model Runtime` and launches the bridge without an explicit unified-config path. The bridge then defaults authority to `.../Role Model Runtime/runtime-config.yaml`, even though current disk state and packaged bridge tests already show a competing `.../Role Model Runtime/state/runtime-config.yaml` convention. That lets a stale singleton canonical alias matrix remain authoritative. Separately, canonical alias re-materialization already exists, but only inside `applyUnifiedRuntimeConfigState(...)`. The later startup `inventory` stage refreshes effective routable inventory and drift warnings but does not persist repaired canonical aliases. As a result, even when startup inventory becomes truthful, canonical aliases can still stay stale long enough for request-time alias resolution to collapse the router's candidate pool to one endpoint.
**Fix Strategy:** Phase 2 should normalize standalone authority onto one explicit unified-config path, migrate or repair legacy candidate files deterministically, and add a post-start canonical-alias repair step that reruns after startup inventory truth is finalized. The fix should preserve custom aliases, keep provider and model agnosticism, and surface authoritative diagnostics when stale truth is detected or repaired.
**Test Plan:** start with RED tests that fail on:
- standalone launcher args not carrying the canonical unified-config path
- legacy root-vs-state config divergence not being normalized deterministically
- startup inventory changes not expanding canonical remote-only aliases after reconciliation
- request-level alias routing still producing singleton `allowEndpoints`
- negative controls for preserved custom aliases and exact-model routing

## Corrective Direction

1. Make the standalone launcher pass one explicit unified-config path instead of relying on the bridge's root-level fallback.
2. Normalize or migrate legacy standalone config candidates deterministically and idempotently so only one authority remains active for the standalone surface.
3. Add a post-start canonical-alias repair step after startup inventory reconciliation becomes authoritative.
4. Persist repaired canonical aliases back to the authoritative config only when the canonical matrix actually changes, preserving custom aliases.
5. Expose authoritative diagnostics for:
   - the selected unified-config path
   - whether legacy-path normalization occurred
   - whether canonical alias drift was detected and repaired
   - whether startup had to degrade because no canonical members remained
6. Protect the fix with strict RED-first launcher and bridge regression tests before any production edits.
