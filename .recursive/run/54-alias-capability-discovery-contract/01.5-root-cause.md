## Data Flow Trace

### GPT Metadata

1. Catalog source contains `openai/gpt-5.4` with correct `1050000 / 128000`.
2. LiteLLM fixture contains `chatgpt/gpt-5.4` with correct `1050000 / 128000`.
3. Runtime endpoint/model ids can use `chatgpt/gpt-5.4`.
4. `resolveRuntimeEndpointCatalogTemplate()` can clone canonical `openai/*` metadata for runtime endpoint registry construction.
5. `backend.listModels()` returns `createRuntimeModelRecords(currentRegistry, currentNormalizedCatalog)`.
6. `createRuntimeModelRecords()` uses exact `modelId` lookup against `currentNormalizedCatalog`, not a shared resolver or the execution catalog with fallback rows.
7. If `chatgpt/gpt-5.4` is not in the exact catalog, the model record falls back to `0 / 0`.

Root cause location: `createRuntimeModelRecords()` and its callers do not use a shared metadata resolver with canonical aliases.

### Downstream Discovery

1. `GET /api/role-model/downstream/openai` resolves aliases from runtime config.
2. It calls `createDownstreamOpenAIProviderConfig(registry, baseUrl, modelAliases)`.
3. `createDownstreamOpenAIProviderConfig()` calls `createModelListResponse()`.
4. `createModelListResponse()` emits OpenAI-compatible list entries only: `id`, `object`, `owned_by`, and `endpoint_ids`.
5. No downstream route computes alias aggregates, target summaries, modalities, tools, reasoning, caching, source attribution, declared-versus-routable layers, freshness, or safe Pi mappings.

Root cause location: downstream discovery is implemented as setup guidance plus a minimal OpenAI model list, not as a versioned role-model discovery contract.

### Capability-Aware Routing

1. Chat Completions and Responses parse request bodies independently.
2. `mapChatCompletionsRequest()` and `mapResponsesRequest()` both build routing requests with hard-coded `requiredCapabilities: ["text.chat"]` and `requiredModalities: ["text"]`.
3. Alias resolution narrows by configured model ids and routable endpoints.
4. No shared inference layer converts image/video content parts, function tools, hosted tools, structured-output controls, or explicit reasoning controls into hard eligibility requirements before scoring.
5. DeepSeek can therefore remain in an alias candidate pool for requests that should require image/video-capable targets unless another unrelated filter removes it.

Root cause location: request capability inference and endpoint eligibility filtering are missing as a first-class pre-scoring layer.

## Root Cause Summary

Root Cause: Role-model currently has no shared model/alias capability resolver and no versioned downstream discovery contract; the existing routes reuse exact-id catalog lookup and minimal OpenAI model-list responses, while request routing hard-codes text-only requirements instead of inferring hard capabilities before alias scoring.

Locations:
- `/role-model-router/apps/runtime-host-bridge/src/index.ts` around `createRuntimeModelRecords()`
- `/role-model-router/apps/runtime-host-bridge/src/index.ts` around `createDownstreamOpenAIProviderConfig()`
- `/role-model-router/apps/runtime-host-bridge/src/index.ts` around `mapChatCompletionsRequest()` and `mapResponsesRequest()`
- `/role-model-router/apps/runtime-host-bridge/src/routable-inventory.ts` around `resolveAliasAllowEndpoints()`

Detailed Explanation:
The catalog already contains enough canonical data for the current GPT/DeepSeek/Kimi pool, and the runtime already has strict alias inventory resolution. The missing layer is a normalized capability contract that joins model metadata, endpoint readiness, alias membership, runtime routability, and request hard requirements. Because that layer does not exist, downstream consumers see only model IDs, Pi fills gaps with hard-coded values, and routing cannot consistently exclude targets that lack requested modalities or capability controls.

Fix Strategy:
- Introduce a shared metadata/capability resolver that understands canonical model IDs such as `chatgpt/* -> openai/*`, preserves source/provenance, and can produce exact target summaries.
- Define a schema-backed downstream discovery contract with exact and alias records, aggregate limits, guaranteed/available/conditional modalities/capabilities, declared-versus-routable layers, freshness metadata, and sanitized fields.
- Integrate that contract into `/api/role-model/downstream/openai` while preserving `/v1/models` compatibility.
- Add shared request capability inference for Chat Completions and Responses, then filter alias candidate endpoints before difficulty/controller/scoring.
- Add stable machine-readable capability failure errors.
- Document Pi-style consumption and verify against an updated runtime plus Pi configuration.

Test Strategy:
- RED tests for GPT metadata resolution and exact model records.
- RED tests for rich `hybrid.hybrid` downstream discovery, all alias records, unknown metadata, declared-versus-routable distinctions, sanitization, freshness, and Pi mapping.
- RED tests for Chat Completions and Responses request-capability inference.
- RED tests proving image/video/tool/structured/reasoning requests filter alias targets before scoring and return stable no-eligible-target errors.
- Schema/fixture validation for the downstream discovery contract.
