## Error Analysis

Telemetry charts could show misleading output because backend analytics did not communicate whether the requested metric or dimension was supported for the selected slice. The frontend therefore treated missing values as ordinary empty chart data.

## Data Flow Trace

Telemetry observations are persisted by the runtime host, read from runtime SQLite storage, aggregated by `POST /api/role-model/telemetry/query`, transported through `runtime-api.ts`, normalized by `telemetry-analytics.ts`, and rendered by `telemetry-charts.tsx`.

## Pattern Analysis

The failure pattern was repeated implicit inference: the backend omitted support metadata, the frontend inferred state from shape, and route consumers applied similar-looking filters through different transport paths.

## Hypothesis Testing

Hypothesis: separating analytics reads from ledger reads and adding backend support metadata will make the frontend chart states deterministic. The GREEN tests validate this by passing full-slice backend aggregation and semantic frontend state assertions.

## Root Cause Summary

The root cause was an under-specified analytics contract: it reused ledger retrieval semantics and did not expose metric/dimension coverage, forcing route-local frontend inference.

## Root Causes

1. Analytics aggregation reused a ledger-oriented row retrieval path that applied a default recent-row limit. The implementation had no separate full-slice analytics read.
2. Metric support was implicit. Aggregators knew how to calculate values, but the response did not expose whether every matched row actually supported the requested metric.
3. Dimension support was implicit. Missing breakdown dimensions produced empty series without a backend-owned explanation of sparsity.
4. Chart state was component-local. The frontend did not have a design-system vocabulary or shared model for semantic telemetry states, so `null`, `0`, and missing series were interpreted inconsistently.
5. Filters were duplicated by caller. Analytics accepted a filter-like body while the request ledger route only accepted URL query params and did not parse the same shared filter set.

## Corrective Direction

- Split analytics aggregation from ledger pagination.
- Add backend-owned applied-query, metadata, metric-support, and dimension-support response fields.
- Compute mixed-support metrics over supported rows and report unsupported coverage separately.
- Add shared runtime UI chart states through the design system before route consumption.
- Send the same shared filters to analytics and request-ledger endpoints.
