## Data Flow Trace

### Trace 1: Code-fence serialization mismatch

1. `resolveAnswerFormat(...)` classifies `h01` and `h02` as `code_fence` cases (`answer-format.ts:156` and suite data).
2. `extractFormattedAnswer(...)` reads the literal fence body but then builds `payload = { code }` and `serialized = JSON.stringify(payload, null, 2)` (`answer-format.ts:554-568`).
3. `runCaseOnEndpoint()` stores that JSON string as `formattedDeliverable` (`benchmark-runner.ts:553`).
4. `resolveJudgeDeliverable(...)` returns `formattedDeliverable?.trim() || actualResponse` (`benchmark-runner.ts:740-741`).
5. `buildJudgeRequestMessages(...)` then hands that JSON wrapper to the judge even though the answer-format instruction still says the final deliverable must be one fenced TypeScript block.

**Trace 1 Root Cause:** the benchmark treats a JSON extraction helper as the authoritative graded deliverable for `code_fence` cases, so the judge can penalize the benchmark’s own wrapper instead of the model’s actual fenced answer.

### Trace 2: Asymmetric overlap grading

1. The manifest records `judgeSubjectOverlap: true` and a warning, meaning overlap is permitted.
2. `orderEndpointsForGrading(...)` changes endpoint order when `judgeSubjectOverlap` is set (`benchmark-runner.ts:133-146`).
3. `gradeWithJudge(...)` computes `judgeSelfGrade = input.gradedEndpointId === input.judgeEndpoint.endpointId && isJudgeSubjectOverlapMode()` and passes `strictSelfGrade` only in that branch (`benchmark-runner.ts:774-788`).
4. `buildJudgeRequestMessages(...)` injects `JUDGE_SELF_GRADE_STRICT_ADDENDUM` only when `strictSelfGrade` is true (`bench-routing/src/index.ts:508-520`).

**Trace 2 Root Cause:** overlap mode is not merely metadata. It changes the substantive grading rubric for exactly one endpoint, so the overlapping judge-subject is held to a stricter contract than its peers.

### Trace 3: Contradictory suite contract

1. `routing-capability-suite.json` defines `h15-max-signal-v3` with `grading_criteria` that require `A/B/C/D sections`.
2. The same case defines an `answer_format` and `example_deliverable` centered on JSON keys such as `plan`, `patch_summary`, and `test_snippet` rather than `A/B/C/D`.
3. `buildJudgeDeliverablesChecklist(...)` turns the grading-criteria text into authoritative `[MUST]` checklist items (`judge-brief.ts:75-113`).
4. `resolveExemplarAnswer(...)` prefers the authored exemplar as if it were compatible (`judge-brief.ts:157-165`).
5. No current suite-validation path rejects the contradiction before execution, so the case can both demand and exemplify incompatible output shapes.

**Trace 3 Root Cause:** authored benchmark data is treated as trustworthy input without a coherence validator, allowing one case to encode mutually exclusive deliverable contracts that then leak directly into judging.

## Root Cause Summary

**Root Cause:** the benchmark currently transforms or contradicts its own deliverable contract after runtime execution, so scoring can diverge from the model’s actual answer for benchmark-internal reasons.
**Location:** `/role-model-router/packages/bench-routing/src/answer-format.ts`, `/role-model-router/apps/runtime-host-bridge/src/benchmark-runner.ts`, `/role-model-router/packages/bench-routing/src/index.ts`, `/role-model-router/packages/bench-routing/src/judge-brief.ts`, `/role-model-router/packages/bench-routing/data/routing-capability-suite.json`
**Detailed Explanation:** local `main` already contains the runtime-side parity fix from run 68, so the remaining failures are now benchmark-owned. `code_fence` answers are wrapped into JSON before grading, overlap mode adds stricter rubric text only for the judge-subject endpoint, and contradictory suite authoring is accepted without validation. Those three seams together explain why the July 13 quick rerun can still report false low scores or inconsistent rankings even when the runtime has already stopped dropping the model’s real output.
**Fix Strategy:** Phase 2 should plan benchmark-owned repairs in this order:
1. write RED tests that fail on the current code-fence wrapper, overlap-only strict rubric, and suite contradictions
2. repair the code-fence judged deliverable so it remains faithful to the authored format
3. remove overlap-only substantive strictness while keeping overlap allowed and warning-visible
4. repair contradictory suite data and add a suite-level validator that fails future contradictions before runtime execution
5. rerun quick and full runtime benchmarks after the unit and integration floor is green
